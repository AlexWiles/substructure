`subs` is the command line for the engine. It runs turns on your machine against
the agents your file declares. It also manages a hosted cloud project.

## Install

```sh
npm install -g @substructure.ai/cli
```

## Running a turn

`subs run` sends one input to the engine, streams the turn, and exits.

```sh
export ANTHROPIC_API_KEY=sk-ant-...
subs run --agent assistant -o pretty "hi"
```

Everything else a run needs is in the file. See [Environments](#environments).

| Flag | Meaning |
| --- | --- |
| `<message>` | The message to send, as a user turn. |
| `--agent` | Which `[agent.<id>]` to run. Without it, the CLI uses `[run].agent` from the file. There is no other default. |
| `--input` | A `ClientInput` in JSON, for anything a plain message cannot say. Its `type` selects submit, resume, or settle. |
| `--session` | Continue a session. Omit it to start one. The CLI prints the id. |
| `--output` | `ag-ui` (default), `jsonl`, or `pretty`. |
| `--db` | The SQLite file. Default `substructure.db`. |

The CLI checks the agent against the file before it creates a session, so a typo
costs nothing and leaves nothing behind. After a turn, it prints the command to
continue the session.

## Environments

One system is one file, and one file is one project. `substructure.toml` says
what your project is. It also holds what you would otherwise pass on every
command. The CLI reads it from the working directory, or from the path you give
with `-c <path>`. It does not search parent directories, so you act on the
directory you are in.

A second environment is a second file, and it gets its own engine. `db` defaults
to the name of the file, so `subs.staging.toml` uses `subs.staging.db` and
`substructure.toml` uses `substructure.db`. Two files in one directory are two
projects. They do not share a database. A relative `db` path is relative to the
file that names it.

A file has two roles. It can have one or both:

| Role | Keys | Commands |
| --- | --- | --- |
| An engine you run | `db`, `log`, `[run]`, `[serve]` | `subs run`, `subs serve` |
| A remote you administer | `[remote]` | `subs apply`, `subs keys`, `subs sessions` |

What the project *is* — `name`, `[agent.<id>]`, `[llm.<id>]`, `[slack]`, and
`[mcp.<id>]` — is one declaration for both roles. So a system you host yourself
is one file. You serve it here and administer it there.

`subs init` asks six questions, one topic at a time. Then it shows you the file
and writes it when you confirm. It writes nothing until the last question.
Everything it does not ask has a default or is a one-line edit.

| Question | Writes |
| --- | --- |
| What the project is called | `name`. `subs apply` creates the project from it. |
| Which provider and which model | `[llm.<provider>]` and the agent's `model` |
| What id the agent has | `[agent.<id>]` |
| Which MCP servers to connect | one `[mcp.<id>]` each, *and* the agent's `mcp` list |
| Whether it answers in Slack, in DMs, and in channels | `[slack]`, one key for each yes |
| Where it runs | `[serve]` for local development, `[remote]` for the cloud |

The MCP question offers some servers by name, and takes a URL for any other
server. It declares each server you pick *and* adds it to the agent, because a
connection that nobody names reaches nothing. Authorize each one with
[`subs mcp login <id>`](./85-connectors.md#authorize-it). The Slack questions are
separate because a DM and a channel reach different people. Answer no to both
and the file gets no [`[slack]`](./105-slack.md) section.

The last question asks where it runs. It writes one section and selects which
list of next steps you get. The cloud answer writes `[remote].url` even though
it equals the default. This way you can read the file to see where it deploys.
That section also sends [`subs mcp login`](./85-connectors.md#authorize-it) to
the deployment, so a connection you authorize before the first `subs apply`
fails with an error instead of storing its credential here. The answer is not
final: `subs link` or the first `subs apply` adds `[remote]` to a local file.

Give a path to write the file somewhere else. The next steps name that path:

```sh
subs init                    # substructure.toml, in this directory
subs init subs.prod.toml     # a second environment, with a name
```

Without a terminal, in CI, a script, or a pipe, `subs init` asks nothing and
writes the local development file. Use `-n` or `--no-interaction` to do the same
in a terminal:

```sh
subs init --no-interaction
```

`subs init` never overwrites a file without telling you. In a terminal it asks.
In a script it fails unless you pass `--force`.

The engine keys describe an engine that runs in this process against a SQLite
file. `subs run` and `subs serve` use them:

```toml title="substructure.toml"
name = "support-bot"
db = "dev.substructure.db"   # events, sessions, and MCP credentials
log = "info"                 # RUST_LOG syntax; $RUST_LOG wins over this

[run]
agent = "support"
output = "pretty"            # ag-ui | jsonl | pretty

[serve]                      # `subs serve` only
host = "127.0.0.1"
port = 8080
auth = false                 # default true. Set false only for a server that
                             # nothing outside this machine can reach

[slack]
agent = "support"            # the default agent for the bot

[slack.channel.C0ENGOPS]     # for a channel that differs
agent = "oncall"

[mcp.sentry]
url = "https://mcp.sentry.dev/mcp"
```

### `[llm.<id>]`

Where a model call runs. The declaration travels with the project. The
credential belongs where the engine runs. The file only names it. It never
holds it.

```toml title="substructure.toml"
[llm.claude]
type = "anthropic"                # anthropic | openai | openrouter | worker
api_key_env = "ANTHROPIC_API_KEY" # optional; defaults from `type`
base_url = "https://…"            # optional

[llm.cheap]
type = "openai"

[llm.byo]
type = "worker"                   # the agent's worker makes the call and
format = "anthropic"              # answers `llm.execute` in this wire shape
```

A block's `type` says who makes the call. With `anthropic`, `openai`, or
`openrouter`, the engine calls the vendor with its own key. With `worker`, the
agent's worker makes the call and the engine holds no key. There is no default
block and no fallback. An agent names a block, or its calls fail with an error
that lists the blocks the file declares.

### `[agent.<id>]`

An agent section has the same fields as the wire `AgentConfig`, with the same
names. It adds three fields that never go on the wire: `description`, `worker`,
and `signing_secret_env`.

```toml title="substructure.toml"
[agent.support]
llm = "claude"                    # required; must name a declared [llm.<id>]
model = "claude-sonnet-4-5"       # required
system = "You are a support agent…"
mcp = ["sentry"]                  # or { id = "sentry", tools = { … } } for fewer tools
sub_agents = ["researcher"]       # ids; each description comes from its own section
tools = [{ name = "confirm", description = "Ask the human", handler = "client" }]

[agent.researcher]
description = "Finds and reads sources"   # what the parent model is told
llm = "cheap"
model = "gpt-5-mini"
system = "Answer with citations. Be brief."

# One agent uses a worker. The others stay with the engine.
[agent.triage]
llm = "claude"
model = "claude-haiku-4-5"
worker = "https://triage.internal/agent"       # decisions POST here
signing_secret_env = "TRIAGE_SIGNING_SECRET"   # named, never written
```

`worker` selects who decides. Set it, and the engine POSTs every decision for
that agent there. Leave it off, and the engine accepts its own proposal. A
decision for an agent that no file declares fails immediately with an error
that lists the agents the file declares. You cannot register an agent later.

Each entry in `tools` must have `handler = "client"`. A file can declare only
the tools a browser runs. The tools a worker runs are worker code.

Every config field is optional. A section has two jobs, and only the first is
required. It declares that the agent **exists** and where its decisions go. It
can also **set** the config. An agent whose worker writes its own config needs
only the first job:

```toml title="substructure.toml"
[agent.reggu]
worker = "http://localhost:4000/substructure/agent"
```

That section sets nothing, so `session.start` carries no proposal and the worker
declares the whole agent. Two rules follow:

- An agent that sets nothing needs a `worker`. Without one, the engine would
  have nothing to propose.
- An agent that sets **anything** needs `llm` and `model`, so that what it sets
  is a config the engine can call with. A partial config is a parse error, not a
  proposal that fails at the first model call.

`[remote]` names a server that speaks `/api/v1`. That can be the hosted cloud, a
deployment you host, or another person's `subs serve`. It also records what this
file is pinned to there. Name the file whatever you like and select it with
`-c`:

```toml title="subs.prod.toml"
name = "support-bot"                  # the project's name. `subs apply` creates the
                                      # project from it, and renames it when it changes

[llm.claude]
type = "anthropic"

[agent.support]
llm = "claude"
model = "claude-sonnet-4-5"
worker = "https://bot.example.com/agent" # `subs apply` pushes this

[mcp.sentry]
url = "https://mcp.sentry.dev/mcp"

[remote]
url = "https://api.substructure.ai"   # optional; this is the default
org = "org_01hx…"                     # written by `subs link` or `subs apply`
project = "proj_01hx…"                # written back by `subs apply` on create
```

Put both halves in one file and it does both. `subs serve` runs it, `subs apply`
administers it, and `subs link` adds `[remote]` to a file that has none.

The turn above becomes:

```sh
subs run "hi"     # `[run].agent` says which agent
```

Precedence is **flag > environment variable > `substructure.toml` > default**.
Setting a value in the file never removes your ability to override it.

The message, `--input`, and `--session` have no key in the file. They say what
one run does, not how the environment is set up. Secrets have no key either. The
file names the variable that holds the signing secret, the same way a connection
names its `token_env`. A key you spell wrong is a parse error, not a setting
that does nothing.

`log` takes `RUST_LOG` syntax: a level on its own, or per-target directives such
as `substructure_core=debug,warn`. It applies from startup, so it covers what
the engine reports while it starts. Without it, `subs run` shows only errors and
`subs serve` shows info.

For `[mcp.<id>]`, see [Connectors](./85-connectors.md).

## Local server

`subs serve` runs the engine as an HTTP server.

```sh
subs serve --no-auth
```

`--no-auth` serves without client or worker authentication. Use it only for a
server that nothing off this machine can reach. The command also takes `--host`,
`--port`, and `--db`. At startup it logs each declared agent, and whether the
engine or a worker decides for it. `--slack-agent <id>` also serves a
[Slack bot](./105-slack.md). You can put all of these in `substructure.toml`
instead.

## Cloud

Sign in and manage a hosted project. One file is one project. A second
environment is a second file: `subs apply -c substructure.staging.toml`.

| Command | Does |
| --- | --- |
| `subs login` / `logout` / `whoami` | Authenticate. |
| `subs apply` | Push the file. It creates the project if the file has no pin, then applies everything the file declares. |
| `subs projects` | List, show, and delete projects. To create or rename one, use `subs apply`. |
| `subs agents` | List and show the declared agents. Rotate an agent's signing secret. |
| `subs llm` | List the declared `[llm.*]` blocks. Set and delete their keys. |
| `subs keys` | Create and revoke API keys. |
| `subs sessions` | List sessions and stream their events. |
| `subs mcp` | Authorize the connections the file declares. |
| `subs slack connect` | Install the Slack app into a workspace, for the org the file pins. |
| `subs doctor` | What the project still needs, and the command for each step. |
| `subs link` | Pin an org and project in the file's `[remote]`. It adds the section if the file has none. |
| `subs config log` | What changed the project's configuration, and who changed it. |

Every cloud command, including `subs login`, uses `--url`. Without it, it uses
the file's `[remote].url`, then `$SUBS_API_URL`, then the hosted cloud. So you
name your own deployment once in `substructure.toml`:

```sh
subs login -c subs.prod.toml     # device flow against the URL the file names
```

The CLI stores credentials for each server, so you can be logged in to several
deployments at once.

### Apply

`subs apply` is the only way to put configuration into a deployment. The file
says what the project should be, and apply makes it so.

```console
$ subs apply -c subs.prod.toml
Created project support-bot (proj_01hy…) in org_01hx…
Pinned proj_01hy… in subs.prod.toml
Applied 4 changes:
  llm.updated             claude (anthropic)
  agent.updated           support -> https://bot.example.com/agent
  mcp.connection_declared sentry (pending authorization)
  mcp.grant_added         sentry
Signing secrets minted:
  support — `subs agents show support`

Action required:

  Authorize the [mcp.sentry] connection
    subs mcp login sentry -c subs.prod.toml

$ subs apply -c subs.prod.toml
No changes.

Action required:

  Authorize the [mcp.sentry] connection
    subs mcp login sentry -c subs.prod.toml
```

If the file pins no `project`, apply creates one. It takes the name from `name`,
then from `--name`, then from a prompt. It writes the pin back into the file and
keeps your comments and layout. Apply is **idempotent**. If the file has not
changed, it writes nothing, prints `No changes.`, and exits 0. So it is safe to
run on every merge.

Apply **replaces**. It does not merge. The file is the whole declaration, so an
agent, an `[llm.*]` block, or a Slack channel that is not in the file is one you
removed:

```console
$ subs apply -c subs.prod.toml
Applied 1 changes:
  agent.removed           triage
```

Apply sends everything the file says about the project: `name`, `[llm.<id>]`,
`[agent.<id>]`, `[mcp.<id>]`, and `[slack]`. It never sends a secret. The
deployment creates each agent's signing secret and holds each block's key. The
file only names variables on your own machine. Apply removes `api_key_env` and
`signing_secret_env` before it sends. A deployment that receives one refuses the
document. It does not ignore the field.

A declared connection does nothing until a person consents. So apply lists the
connections that still need consent, and the command for each one. The list is
the current state, not a record of this run, so an apply with no changes still
shows it. `subs doctor` shows it at any time.

`subs config log` shows the history, whichever command wrote it:

```console
$ subs config log -c subs.prod.toml
2026-07-30 14:02  alex@…  apply  config.applied           hash 6f2a1c9d4b7e
2026-07-30 14:02  alex@…  apply  mcp.grant_added          sentry
2026-07-30 14:02  alex@…  apply  mcp.connection_declared  sentry (pending authorization)
2026-07-30 14:02  alex@…  apply  agent.updated            support -> https://bot.example.com/agent
2026-07-30 14:02  alex@…  apply  llm.updated              claude (anthropic)
2026-07-30 14:02  alex@…  apply  project.created          support-bot
```

### Agents and keys

An agent exists because the file declares it, so there is nothing to create. The
deployment owns the part the file cannot hold:

```console
$ subs agents list
ID       LLM     MODEL                HOSTING                          SECRET
support  -       -                    https://bot.example.com/agent    set
triage   claude  claude-sonnet-4-5    engine                           -

$ subs agents show support          # includes the signing secret
$ subs agents rotate-secret support # owner only

$ subs llm list
NAME    TYPE       KEY
claude  anthropic  set

$ subs llm set-key claude              # from stdin
$ subs llm set-key claude --env MY_KEY # or from an environment variable
```

A key never appears in the command line, and no read ever returns one.

### Slack

You connect a workspace to the org, and the deployment holds the bot token:

```console
$ subs slack connect
Open this URL to add the bot to your workspace:
  https://slack.com/oauth/v2/authorize?…
Opened your browser to install.
Connected Acme (T0123ABC) to org_01hx…
```

`[slack]` in the file routes a message to an agent, and `subs apply` sends that
routing to the deployment. A connected workspace with no `[slack]` is a bot that
never answers. If the file names no `[remote]`, or the deployment installs no
Slack app, the command prints the Socket Mode steps instead, because you hold
that bot's credential. See [Slack](./105-slack.md).

### Doctor

`subs doctor` lists every step nobody has finished, however the project runs:

```console
$ subs doctor -c subs.prod.toml

Action required:

  Connect a Slack workspace
    subs slack connect -c subs.prod.toml

  Set the key for [llm.claude]
    subs llm set-key claude -c subs.prod.toml
```

If the file names a `[remote]`, doctor asks the deployment, because it holds the
keys, the consents, and the workspaces. If the file names none, it describes an
engine you run here, so doctor reads the same list from this machine: the
variables that are empty, and the connections its database has no credential
for:

```console
$ subs doctor

Action required:

  Set $ANTHROPIC_API_KEY, the key for [llm.claude] (https://console.anthropic.com/settings/keys)
    export ANTHROPIC_API_KEY=...

  Authorize the [mcp.linear] connection
    subs mcp login linear
```

`subs llm set-key`, `subs mcp login`, and `subs slack connect` each print what is
left when they finish. So you set up a project by following one command to the
next. `--json` prints the list as JSON. With nothing left, doctor prints
`Nothing to do.`
