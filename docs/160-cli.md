`subs` is the command-line front end to the engine. It runs turns locally
against the agents your file declares and manages a hosted cloud project.

## Install

```sh
npm install -g @substructure.ai/cli
```

## Running a turn

`subs run` sends one input to the engine, streams the turn, and exits.

```sh
export ANTHROPIC_API_KEY=sk-ant-...
subs run --agent assistant -o pretty "hi"
```

Everything else the run needs is in the file — see [Environments](#environments).

| Flag | Meaning |
| --- | --- |
| `<message>` | The message to send, as a user turn. |
| `--agent` | Which `[agent.<id>]` to run. Falls back to `[run].agent` when the file pins one; there is no other default. |
| `--input` | A `ClientInput` JSON, for anything a plain message cannot say. Its `type` picks submit, resume, or settle. |
| `--session` | Resume a session. Omit to start one; the id is printed. |
| `--output` | `ag-ui` (default), `jsonl`, or `pretty`. |
| `--db` | SQLite file. Default `substructure.db`. |

The agent is checked against the file before a session is created, so a typo
costs nothing and leaves nothing behind. After a turn it prints the command to
continue the session.

## Environments

One system is one file, and one file is one project. `substructure.toml`
describes what your project is, and
holds what you would otherwise pass on every command. The CLI reads it from the
working directory, or takes `-c <path>` — no parent directories are searched, so
where you stand is what you act on.

A second environment is a second file, and it gets its own engine: `db` defaults
to the file's own name, so `subs.staging.toml` uses `subs.staging.db` while
`substructure.toml` uses `substructure.db`. Two files in a directory are two
projects rather than one database they share. A relative `db` sits beside the
file that names it.

A file carries two roles, either or both:

| role | keys | commands |
| --- | --- | --- |
| an engine you run | `db`, `log`, `[run]`, `[server]` | `subs run`, `subs serve` |
| a deployment you administer | `[deployment]` | `subs apply`, `subs keys`, `subs sessions` |

What the project *is* — `name`, `[agent.<id>]`, `[llm.<id>]`, `[slack]`,
`[mcp.<id>]` — is one declaration whichever role reads it. A self-hosted system
is therefore one file: serve it here, administer it there.

`subs init` asks the two things it cannot guess — which LLM provider, and what
the agent is called — shows you the file, and writes it once you confirm. It
tells you which environment variable the provider expects, and nothing is
written until the last question. Everything else has a default, a flag, or is a
one-line edit.

It writes a file describing an engine you run here. Add `deployment` or `both`
to get a `[deployment]` section as well, and a path to write somewhere other
than here:

```sh
subs init                              # an engine you run here
subs init both                         # …and a deployment to administer
subs init deployment subs.prod.toml    # only the deployment half, named
```

The role is not a question, because it is not a decision the file forces: `subs
link` and `subs apply` add `[deployment]` themselves the first time you deploy,
so a file that starts local can be deployed later without being re-initialized.

Without a terminal — CI, a script, a pipe — `subs init` writes the starter file
and asks nothing. `-n`/`--no-interaction` forces that in a terminal too:

```sh
subs init --no-interaction
```

An existing file is never overwritten silently: the wizard asks, and the
scripted path fails unless you pass `--force`.

The engine keys describe one running in this process against a SQLite file —
what `subs run` and `subs serve` drive:

```toml title="substructure.toml"
name = "support-bot"
db = "dev.substructure.db"   # events, sessions, and MCP credentials
log = "info"                 # RUST_LOG syntax; $RUST_LOG still wins

[run]
agent = "support"
output = "pretty"            # ag-ui | jsonl | pretty

[server]                     # `subs serve` only
host = "127.0.0.1"
port = 8080
auth = false                 # default true. Off is for a server nothing
                             # outside this machine can reach

[slack]
agent = "support"            # the default agent for the bot

[slack.channel.C0ENGOPS]     # where one channel differs
agent = "oncall"

[mcp.sentry]
url = "https://mcp.sentry.dev/mcp"
```

### `[llm.<id>]`

What a model call runs on. The declaration travels with the project; the credential
binds where the engine runs, and is always *named*, never written.

```toml title="substructure.toml"
[llm.claude]
type = "anthropic"                # anthropic | openai | openrouter | worker
api_key_env = "ANTHROPIC_API_KEY" # optional; defaults from `type`
base_url = "https://…"            # optional

[llm.cheap]
type = "openai"

[llm.byo]
type = "worker"                   # the agent's own worker makes the call,
format = "anthropic"              # answering `llm.execute` in this wire shape
```

A block's `type` is the execution venue: `anthropic`/`openai`/`openrouter` mean
the engine calls the vendor with a key of its own; `worker` means the agent's
worker does it and the engine never holds a key. There is no default block and
no fallback chain — an agent names one, or its calls fail saying what was
declared.

### `[agent.<id>]`

An agent section mirrors the wire `AgentConfig` — same field names — plus the
two that never cross the wire: `worker` and `signing_secret_env`.

```toml title="substructure.toml"
[agent.support]
llm = "claude"                    # required; must name a declared [llm.<id>]
model = "claude-sonnet-4-5"       # required
system = "You are a support agent…"
mcp = [{ id = "sentry" }]
sub_agents = [{ id = "researcher", description = "Finds and reads sources" }]
tools = [{ name = "confirm", description = "Ask the human", handler = "client" }]

[agent.researcher]
llm = "cheap"
model = "gpt-5-mini"
system = "Answer with citations. Be brief."

# One agent hosted by a worker; the rest stay engine-hosted.
[agent.triage]
llm = "claude"
model = "claude-haiku-4-5"
worker = "https://triage.internal/agent"       # decisions POST here
signing_secret_env = "TRIAGE_SIGNING_SECRET"   # named, never written
```

`worker` is the whole routing switch. Set it and the engine POSTs every decision
for that agent there; leave it off and the engine decides by accepting its own
proposal. An agent nobody declared fails its first decision immediately, saying
what *is* declared — there is no register-later flow.

`tools` here must be `handler = "client"`: a file can only declare the tools a
browser runs, because worker-executed tools are worker code.

Every config field is optional, because a section has two jobs and only the
first is required: it declares that the agent **exists** and where its decisions
go, and it may also **seed** the config. An agent whose worker authors its own
identity needs only the first:

```toml title="substructure.toml"
[agent.reggu]
worker = "http://localhost:4000/substructure/agent"
```

That seeds nothing, so `session.start` carries no proposal and the worker
declares the agent exactly as it would have before the file could. The two
rules that follow from it:

- An agent that seeds nothing needs a `worker` — the engine would have nothing
  to propose from otherwise.
- An agent that seeds **anything** needs `llm` and `model`, so that what it
  seeds is a config the engine can actually call with. A half-declared one is a
  parse error rather than a proposal that fails at the first model call.

`[deployment]` names a server speaking `/api/v1` — the hosted cloud, a
self-hosted deployment, or someone else's `subs serve` — and what this file is
pinned to there. Name the file whatever you like and select it with `-c`:

```toml title="subs.prod.toml"
name = "support-bot"                  # the project's name; `subs apply` creates
                                      # the project from it, and renames when it changes

[llm.claude]
type = "anthropic"

[agent.support]
llm = "claude"
model = "claude-sonnet-4-5"
worker = "https://bot.example.com/agent" # `subs apply` pushes this

[mcp.sentry]
url = "https://mcp.sentry.dev/mcp"

[deployment]
url = "https://api.substructure.ai"   # optional; this is the default
org = "org_01hx…"                     # written by `subs link` or `subs apply`
project = "proj_01hx…"                # written back by `subs apply` on create
```

Add both halves to one file and it does both: `subs serve` runs it, `subs apply`
administers it, and `subs link` adds `[deployment]` to a file that had none.

The turn above becomes:

```sh
subs run "hi"     # `[run].agent` says which agent
```

Precedence is **flag > environment variable > `substructure.toml` > default**,
so pinning a setting never takes an override away.

The message, `--input`, and `--session` have no entry: they say what one run
does, not how the environment is set up. Neither do secrets — the file names the variable holding
the signing secret, the same way a connection names its `token_env`. A
misspelled key is a parse error rather than a setting that silently does
nothing.

`log` takes `RUST_LOG` syntax — a bare level, or per-target directives like
`substructure_core=debug,warn`. It applies from startup, so it covers what the
engine says while coming up. Without it, `subs run` shows errors only and
`subs serve` shows info.

See [Connectors](./85-connectors.md) for `[mcp.<id>]`.

## Local server

`subs serve` runs the engine as an HTTP server.

```sh
subs serve --no-auth
```

`--no-auth` serves without client or worker authentication, for a server nothing
off this machine can reach. It also takes `--host`, `--port`, and `--db`. On
startup it logs each declared agent and whether the engine or a worker decides
for it.
`--slack-agent <id>` serves a [Slack bot](./105-slack.md) alongside. Every one of
these can live in `substructure.toml` instead.

## Cloud

Sign in and manage a hosted project. One file is one project; a second
environment is a second file (`subs apply -c substructure.staging.toml`).

| Command | Does |
| --- | --- |
| `subs login` / `logout` / `whoami` | Authenticate. |
| `subs apply` | Push the file: create the project if unpinned, then everything it declares. |
| `subs projects` | List, show, delete projects. Creating and renaming are `subs apply`. |
| `subs agents` | List and show the declared agents; rotate an agent's signing secret. |
| `subs llm` | List the declared `[llm.*]` blocks; set and delete their keys. |
| `subs keys` | Create and revoke API keys. |
| `subs sessions` | List sessions and stream their events. |
| `subs mcp` | Authorize the connections the file declares. |
| `subs link` | Pin an org and project in the file's `[deployment]`, adding the section if it has none. |
| `subs config log` | What has changed the project's configuration, and who changed it. |

Every cloud command — `subs login` included — targets `--url`, else the file's
`[deployment].url`, else `$SUBS_API_URL`, else the hosted cloud, so a
self-hosted deployment is named once in `substructure.toml`:

```sh
subs login -c subs.prod.toml     # device flow against the url the file names
```

Credentials are stored per server, so logins to several deployments coexist.

### Apply

`subs apply` is the only way configuration enters a deployment: the file says
what the project should be, and applying makes it so.

```console
$ subs apply -c subs.prod.toml
Created project support-bot (proj_01hy…) in org_01hx…
Pinned proj_01hy… in subs.prod.toml
Applied 4 changes:
  llm.updated             claude (anthropic)
  agent.updated           support -> https://bot.example.com/agent
  mcp.connection_declared sentry (pending authorization)
  mcp.grant_added         sentry
Signing secrets minted:
  support — `subs agents show support`
Pending authorization:
  sentry — run `subs mcp login sentry -c subs.prod.toml` or authorize in the dashboard

$ subs apply -c subs.prod.toml
No changes.
```

With no `project` pinned it creates one — from `name`, else `--name`, else a
prompt — and writes the pin back into the file with your comments and layout
intact. It is **idempotent**: re-applying an unchanged file writes nothing,
prints `No changes.`, and exits 0, which makes it safe to run on every merge.

It **replaces** rather than merges. The file is the whole declaration, so an
agent, `[llm.*]` block, or Slack channel absent from it is one that was removed:

```console
$ subs apply -c subs.prod.toml
Applied 1 changes:
  agent.removed           triage
```

What it applies is everything the file says about the project: `name`,
`[llm.<id>]`, `[agent.<id>]`, `[mcp.<id>]`, and `[slack]`. Never a secret — the
deployment mints each agent's signing secret and holds each block's key, and the
file only ever names variables on your own machine. `api_key_env` and
`signing_secret_env` are stripped before send; a deployment that receives one
rejects the document rather than ignoring the field.

A declared connection is inert until a human consents, so apply lists what is
still pending and the command that finishes it.

`subs config log` shows the history, whichever surface wrote it:

```console
$ subs config log -c subs.prod.toml
2026-07-30 14:02  alex@…  apply  config.applied           hash 6f2a1c9d4b7e
2026-07-30 14:02  alex@…  apply  mcp.grant_added          sentry
2026-07-30 14:02  alex@…  apply  mcp.connection_declared  sentry (pending authorization)
2026-07-30 14:02  alex@…  apply  agent.updated            support -> https://bot.example.com/agent
2026-07-30 14:02  alex@…  apply  llm.updated              claude (anthropic)
2026-07-30 14:02  alex@…  apply  project.created          support-bot
```

### Agents and keys

An agent exists because the file declares it, so there is nothing to create.
What the deployment owns is the half the file cannot hold:

```console
$ subs agents list
ID       LLM     MODEL                HOSTING                          SECRET
support  -       -                    https://bot.example.com/agent    set
triage   claude  claude-sonnet-4-5    engine                           -

$ subs agents show support          # includes the signing secret
$ subs agents rotate-secret support # owner only

$ subs llm list
NAME    TYPE       KEY
claude  anthropic  set

$ subs llm set-key claude              # from stdin
$ subs llm set-key claude --env MY_KEY # or from an environment variable
```

A key never appears in argv, and no read ever returns one.
